# Python Project: Архитектурная эволюция

Этот репозиторий — наглядное пособие по рефакторингу. Здесь показан путь проекта от рабочего, но "грязного" прототипа до чистой, масштабируемой архитектуры на Python.

## 🎯 Зачем этот репозиторий?

Чтобы показать, как я учусь видеть недостатки в собственном коде и исправлять их. Вместо того чтобы просто переписать и забыть, я сохранил все этапы развития — от монолита до применения паттернов проектирования.

## 📈 Этапы развития (Смотрите вкладку Commits)

### 🟢 Stage 1: Монолит (MVP)
* **Что это:** Весь код в одном файле.
* **Зачем:** Быстро проверить идею и заставить её работать.
* **Проблема:** Невозможно читать, любые изменения ломают всё, дублирование кода.

### 🟡 Stage 2: Модульность
* **Что это:** Код разбит на несколько файлов по смыслу.
* **Зачем:** Навести порядок, убрать дублирование, разделить ответственность.
* **Проблема:** Всё ещё много глобальных состояний и жестких связей между модулями.

### 🔴 Stage 3: ООП и Чистая Архитектура
* **Что это:** Полная переработка на Объектно-Ориентированном Программировании.
* **Зачем:** Сделать код расширяемым, тестируемым и понятным.
* **Результат:** Логика инкапсулирована в классы, легко добавлять новые фичи, не ломая старые.

### 🔵 Stage 4: Углублённое ООП, паттерны и UX (Текущая версия)
* **Что это:** Внедрение наследования, фабричного паттерна и улучшение пользовательского интерфейса.
* **Ключевые решения:**
  - **Наследование вместо булевых флагов:** замена поля `urgent: bool` на иерархию классов `Request → UrgentRequest / ScheduledRequest` (принцип "Replace Conditional with Polymorphism").
  - **Фабричный метод** `request_from_dict()` для корректной десериализации полиморфных объектов из JSON с обратной совместимостью старых данных.
  - **Разделение по принципу единственной ответственности (SRP):** `models.py` (доменная модель), `Operations.py` (бизнес-логика), `HelpOperations.py` (фильтры/поиск), `DownloadAndSaveFileData.py` (сериализация), `TableUtils.py` (отрисовка).
  - **TUI через ANSI-коды** (`\033[2J\033[H`) вместо скроллинга консоли, с универсальной функцией `draw_table()`.
  - **Адаптивное меню:** пункт редактирования меняется динамически в зависимости от типа объекта.
* **Результат:** Код стал типобезопасным, расширяемым и удобным для пользователя. Условная логика в UI-слое устранена.

* **UX:** ANSI TUI, табличная отрисовка
